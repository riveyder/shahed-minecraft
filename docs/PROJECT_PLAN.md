## Исходное ограничение этапа 1

Последнее распоряжение пользователя о порядке разработки имеет приоритет над требованием исходного задания сразу сделать MVP с полётом и FPV-камерой. В текущем задании выполняется **только рабочая основа**. После её завершения работа останавливается до следующего задания пользователя.

В объём этапа 1 входят:

1. Полное техническое задание и архитектурный план в этом файле.
2. README с установкой, сборкой, перечнем функций, честными статусами и дорожной картой.
3. Настоящий Fabric-проект для Minecraft Java Edition **26.2**, совместимые Java, Gradle Wrapper, Fabric Loader, Fabric API и GitHub Actions.
4. Зарегистрированная сущность дрона, предмет пульта и предмет FPV-очков.
5. Первоначальная узнаваемая трёхмерная модель дрона: силуэт крыла, корпус, двигатель/винт, правильное направление носа и собственная серо-белая текстура с маркировкой. Это начальная модель, а не заявление о завершении всех будущих анимаций.
6. Команды получения оборудования и создания дрона в творческом режиме, с проверкой источника команды и условий выполнения на сервере.
7. Сборка `./gradlew build`, исправление выявленных ошибок и подготовка изменений к сохранению в GitHub.

**В этом этапе не реализуются:** FPV-камера и HUD, полноценное управление полётом, физика режимов Arcade/Advanced, привязка и сеансы управления, реплеи, звук, боевые столкновения/взрывы, расширенная многопользовательская логика, гонки, наблюдатель и остальные расширения. Наличие зарегистрированного предмета не означает работающего управления. Сущность, которую можно создать командой, ещё не является управляемым дроном.

Не следует добавлять пустые заглушки будущих подсистем и представлять их как работающие функции. На этапе 1 точки расширения определяются границами ответственности и документацией; интерфейсы и реализации добавляются тогда, когда появляется проверяемое поведение.

## Платформа и проверка достоверности

Целевая версия игры — 26.2. Совместимые версии Java, Gradle, Fabric Loader, Fabric API и инструмента сборки следует закрепить в проекте только после проверки официальных опубликованных данных. На момент составления этого плана конкретные версии ещё проверяются; этот документ не выдумывает их и не утверждает, что сборка уже выполнена.

Авторитетные источники:

- Релизы Minecraft: <https://www.minecraft.net/en-us/articles>.
- Метаданные Fabric Loader: <https://meta.fabricmc.net/>.
- Официальный Maven Fabric: <https://maven.fabricmc.net/>.
- Документация разработки Fabric: <https://docs.fabricmc.net/develop/>.
- Совместимость Gradle с Java: <https://docs.gradle.org/current/userguide/compatibility.html>.

Если официальная 26.2 или необходимая зависимость ещё не опубликована, следует явно зафиксировать блокер. Нельзя незаметно подменять целевую версию снапшотом, 26.1 или старой веткой. Сборка на иной версии может быть только отдельно обозначенным экспериментом и не считается выполнением требования 26.2.

Доказательства готовности должны быть разделены:

- `./gradlew build` подтверждает компиляцию, упаковку и настроенные проверки.
- Запуск клиента подтверждает загрузку ресурсов, видимость предметов и правильность модели.
- Запуск выделенного сервера подтверждает отсутствие клиентских классов в общем entrypoint и работоспособность серверной регистрации.
- Проверка несколькими игроками подтверждает только реально проверенные сетевые сценарии; она не заменяется одной успешной сборкой.

Фактические версии, команды и результаты проверки фиксируются в README и итоговом отчёте. Эта архитектура сама по себе не является протоколом успешных испытаний.

## Архитектура

### Границы общего и клиентского кода

Базовый Java-пакет определяется проектом. Ниже указаны его логические подпакеты, а не обещание наличия ещё не реализованных классов.

| Область | Ответственность | Ограничение |
| --- | --- | --- |
| `common` / общий entrypoint | Идентификаторы мода, общий жизненный цикл, вызов регистрации | Не импортирует рендерер, окно, камеру или другие клиентские классы |
| `entity` | Тип сущности дрона, его базовое состояние, сохранение существующих данных | Игровое состояние принадлежит серверу; визуализация вынесена отдельно |
| `item` | Регистрация пульта и FPV-очков, общие свойства предметов | Предметы этапа 1 не запускают ещё не существующие сеансы FPV |
| `command` | Серверные команды тестового оборудования и создания сущности | Проверяет права и творческий режим; использует переводы для сообщений |
| `client` | Клиентский entrypoint, renderer, модель, клиентские регистрации | Подключается только в клиентской среде |
| `client.model` / `client.render` | Геометрия, текстура, ориентация и отрисовка дрона | Не определяет физику и не меняет авторитетное положение сущности |
| `port` / версионные адаптеры | Узкие границы вызовов API Minecraft/Fabric, меняющихся между версиями | Один JAR рассчитан на одну закреплённую версию игры |
| Ресурсы | Метаданные Fabric, модели предметов, текстуры, переводы и последующие ассеты | Общие ресурсы и клиентская отрисовка не смешиваются с серверной логикой |

Версионную границу следует проводить там, где она уменьшает связанность: регистрация, сериализация состояния сущности и предметов, команды, рендеринг, ввод и будущая камера. Не нужно строить общий движок совместимости с несколькими Minecraft-версиями или оборачивать каждый метод ради абстракции. Перенос на другую версию выполняется отдельным обновлением зависимостей и затронутых адаптеров.

### Модель и направление

Модель должна иметь явно определённые нос, хвост, ось крыла и положение винта. Геометрия строится в локальных координатах; renderer применяет единственное согласованное преобразование локального направления к yaw сущности. Поворот не следует одновременно компенсировать в геометрии, renderer и будущей физике.

При ручной проверке дрон создаётся в нескольких направлениях, и нос сопоставляется с направлением его взгляда. На этапе полёта та же система координат станет основой тяги и положения FPV-камеры. Визуальный винт и будущая анимация не должны изменять физическую ориентацию сущности.

### Будущие сеансы управления и безопасность сервера

При реализации следующего этапа сервер будет проверять команды управления и владеть положением, скоростью, столкновениями, доступом и жизненным циклом дрона. Клиент передаёт ограниченный ввод, а не произвольную готовую позицию. Пакеты проверяются по отправителю, существованию сущности, измерению, разрешению владельца, допустимому состоянию и диапазонам значений. Требуются ограничения частоты ввода и числа активных дронов.

У каждого дрона есть UUID сущности. Будущая постоянная привязка пульта хранит UUID дрона и необходимые данные привязки в поддерживаемом игрой формате. Сетевой числовой ID сущности не заменяет постоянный UUID. Серверная запись владения и разрешения на совместное управление являются источником прав; изменение клиентского предмета не должно позволять захватить чужой дрон.

Сеанс пилота должен явно связывать игрока, дрон, измерение и состояние подключения. Состояния могут включать ожидание подключения, активное управление, потерю сигнала и завершение. При отключении игрока, удалении или уничтожении дрона, смене измерения и остановке сервера требуется освобождать сеанс и связанные ресурсы. Повторное завершение должно быть безопасным. Подключение наблюдателя — отдельный доступ без права выдавать управляющий ввод.

Тело игрока остаётся в мире: без телепортации к дрону, удаления сущности игрока или превращения самого игрока в дрон. FPV меняет клиентскую точку наблюдения и ввод, а сервер сохраняет обычное существование тела. При штатном выходе и аварийной очистке восстанавливаются камера, управление и интерфейс. Будущий эффект потери сигнала сохраняет предусмотренное исходным ТЗ поведение экрана до выхода пользователя; для отключения клиента и завершения сессии всё равно обязательна безопасная очистка.

### Будущие подсистемы

- **Полёт:** чистые структуры ввода и состояния, конфигурация ограничений и сменная модель `Arcade` / `Advanced`; общий серверный цикл и клиентская интерполяция. Режим Advanced не требует реальных беспилотных систем или внешних интеграций.
- **FPV:** камера и HUD читают состояние сеанса/телеметрию. Они не рассчитывают авторитетную физику. Минимальный/расширенный HUD, чувствительность, инверсия и плавность — отдельные пользовательские настройки.
- **Сеть:** сообщения привязки, подключения, ввода, телеметрии и событий разделены по назначению. Сервер проверяет разрешения и конечные значения, клиент сглаживает подтверждённые данные. Не удерживать лишние чанки ради полёта без явно выбранной политики.
- **Звук:** игровая телеметрия управляет параметрами звукового слоя. Пространственный звук мира и приглушённый канал пилота разделены. Все используемые аудиоассеты должны иметь понятное происхождение и разрешение.
- **Повреждения:** серверная модель состояния и причины завершения; отдельно настраиваются урон сущностям, разрушение блоков, сила игрового эффекта, лимиты дронов и задержка повторного запуска. Тренировочный режим отключает опасные игровые последствия.
- **Реплеи:** ограниченный кольцевой буфер последних 10 секунд на дрон; предел частоты/числа образцов и лимит активных записей. Хранятся отметка времени, положение, ориентация и необходимые визуальные события. Воспроизведение локально для выбранного зрителя, не останавливает сервер и не повторяет урон, взрывы или изменения мира. Буферы и сессии очищаются при завершении и удалении сущностей.
- **Чёрный ящик:** компактная сводка последнего полёта — длительность, максимальная скорость/высота, причина завершения. Она отделена от ограниченного буфера реплея и не требует сохранять бесконечную историю.
- **Конфигурация:** сервер определяет игровые ограничения, доступ и ущерб; клиент хранит ввод, HUD, камеру и звук. Значения проверяются, а отсутствующие поля получают безопасные значения по умолчанию.
- **Локализация и фирменный стиль:** украинский основной интерфейс, английский и русский переводы; стабильные ключи перевода вместо встроенных строк. Фирменные сообщения ненавязчивы и не засоряют чат.

Обсуждавшиеся идеи обязательны к сохранению в плане, но **не считаются реализованными на этапе 1**:

- **Arcade:** доступный полёт с инерцией и простым управлением.
- **Advanced:** более сложные крен, тангаж и тяга; отдельные настройки игрока.
- **Тренировочный дрон:** посадка и повторное использование без разрушительных последствий.
- **Гонки:** контрольные точки, таймер и проверяемое сервером прохождение маршрута.
- **Наблюдатель:** разрешённый владельцем просмотр камеры без перехвата управления.
- **Ночное видение:** переключаемый игровой фильтр с зелёным оттенком.
- **Повреждения:** понятное состояние дрона, причины аварии и настраиваемые игровые последствия.
- **Чёрный ящик:** сводка последнего полёта и его завершения.
- **Кастомизация:** варианты окраски, маркировки, внешних элементов и оборудования без необходимости менять базовую архитектуру; игровые характеристики определяет сервер.
- **Режим режиссёра:** кинематографические ракурсы, свободная камера и инструменты просмотра в рамках разрешённого сеанса; не управление чужими дронами и не изменение мира при реплее.
- **Юмористические сообщения:** «Зв'язок загубився десь у Житомирі», «Гарантія анульована», «Операторе, у нас проблеми», «Політ завершено. Причина: дерево» и другие переведённые необязательные реплики бренда.

## Проверка и подготовка к сохранению

Для текущего этапа обязательна реальная команда `./gradlew build`. При ошибке устраняется конкретная причина и повторяется затронутая проверка. Успех Gradle нельзя заменять успешным скачиванием зависимостей. В CI та же сборка должна публиковать созданный JAR как GitHub Actions Artifact; наличие workflow ещё не доказывает успешный удалённый запуск.

Для модели и загрузки мода необходим отдельный ручной сценарий: установить совместимые игру/Loader/API, открыть творческий мир, получить предметы, создать дрон, проверить ориентацию и текстуру, сохранить/загрузить мир; затем проверить загрузку общего кода выделенным сервером. Если такой запуск в облаке не выполнен, это явно указывается как оставшаяся проверка.

На следующих этапах автоматические тесты полезны для чистой логики привязок, прав, валидации сообщений, конфигурации и кольцевого буфера. Они добавляются вместе с соответствующим поведением, а не как формальные проверки ещё отсутствующих подсистем.

Перед передачей проверяются `git diff`, новые файлы и исключения сборочных выходов/кэшей. Секреты и локальные кэши в Git не добавляются. Подготовка изменений к сохранению не означает, что они уже отправлены в удалённый GitHub или что CI там уже завершился. Отчёт этапа перечисляет реализованное, созданные файлы, точный результат сборки, ограничения и конкретный следующий шаг. **Этап 2 не начинается без нового задания.**

# ЗАДАНИЕ ДЛЯ CODEX: Создание Minecraft-мода SHAHED.exe — FPV Mayhem

Ты выступаешь как ведущий Java-разработчик Minecraft-модов, специалист по Fabric, игровым камерам, 3D-рендерингу, сетевой синхронизации и интерфейсам.

Твоя задача — самостоятельно создать в текущем GitHub-репозитории полноценный Minecraft-мод с управляемыми FPV-дронами.

Это не обычный демонстрационный мод. Нужен качественный игровой проект с приятным управлением, оригинальными механиками, звуками, интерфейсами и поддержкой многопользовательских серверов.

**Название:** SHAHED.exe — FPV Mayhem

**Вымышленный производитель:** ТОВ «КРИВІ РУКИ AEROSPACE»

**Девиз:** «Злетіти легко. Посадити — не обіцяємо».

Проект является юмористическим игровым симулятором внутри Minecraft. Реализуй все механики исключительно игровыми средствами без интеграции с реальными беспилотными системами.

## 1. Техническая платформа

- Minecraft Java Edition 26.2.
- Fabric Loader и Fabric API.
- Java и Gradle версий, совместимых с выбранной версией игры.
- Поддержка одиночной игры и выделенного сервера.
- Код Java, аккуратная модульная архитектура.
- Работа без обязательных сторонних модов, кроме необходимых зависимостей Fabric.
- Возможность последующего переноса на другие версии Minecraft.

Проверь актуальные версии зависимостей по официальной документации. Не используй выдуманные API.

Создай Gradle Wrapper, исходники, ресурсы, конфигурации, README и необходимые файлы проекта.

Не пытайся обеспечить совместимость одного JAR со всеми версиями Minecraft. Вместо этого изолируй версионно-зависимый код для последующего портирования.

## 2. Основной игровой цикл

Игрок создаёт или получает FPV-дрон, пульт управления и FPV-очки.

Затем:

1. Размещает дрон в игровом мире.
2. Привязывает пульт к конкретному дрону.
3. Привязывает очки к своему пульту или комплекту оборудования.
4. Надевает FPV-очки.
5. Активирует пульт.
6. Видит анимацию подключения.
7. Камера переключается на точку зрения дрона.
8. Открывается полноэкранный интерфейс управления.
9. Игрок управляет полётом.
10. После выхода возвращается к обычному игровому персонажу.

Во время управления тело игрока остаётся в мире, не телепортируется и не исчезает.

При уничтожении дрона видеосигнал обрывается.

## 3. Многопользовательский режим

Это один из главных приоритетов.

На одном сервере одновременно могут находиться несколько игроков со своими дронами.

Каждый дрон должен иметь уникальный UUID.

Каждый пульт хранит идентификатор привязанного дрона.

Обязательно реализуй:

- Независимое управление дронами разных игроков.
- Серверную проверку прав доступа к управлению.
- Невозможность случайно захватить чужой дрон.
- Корректную синхронизацию положения и поворотов.
- Видимость полёта для других игроков.
- Сохранение привязки оборудования.
- Корректную обработку отключений игроков от сервера.
- Защиту от управления несуществующим или уничтоженным дроном.
- Синхронизацию звуков и визуальных эффектов.

Сервер должен быть авторитетным относительно положения дронов, столкновений и игровой логики.

Предусмотри конфигурацию разрешений на совместное управление.

## 4. Управление полётом

Сделай управление удобным, плавным и отзывчивым.

Реализуй аркадную модель полёта с инерцией и возможностью последующего расширения до более сложной симуляции.

Предусмотри:

- Управление тягой двигателя.
- Набор и снижение высоты.
- Поворот влево и вправо.
- Крен.
- Тангаж.
- Плавное ускорение.
- Ограничение максимальной скорости.
- Влияние скорости на управляемость.
- Инерцию при изменении направления.
- Управление мышью.
- Возможность настройки клавиш.

Добавь два режима:

**Arcade:** простой, удобный полёт, рассчитанный на весёлую игру с друзьями.

**Advanced:** более сложное управление креном, тангажом и тягой.

Настройки должны сохраняться отдельно для каждого игрока.

Добавь настройку чувствительности, инверсии мыши, плавности управления и поведения камеры.

## 5. Трёхмерная модель дрона

Создай отдельную игровую сущность с 3D-моделью, напоминающей стилизованный Shahed-136.

Модель должна иметь:

- Характерный треугольный силуэт крыла.
- Корпус подходящих пропорций.
- Серо-белую текстуру.
- Вращающийся винт.
- Видимые элементы двигателя.
- Фирменную маркировку вымышленного производителя.
- Анимации в полёте.

Избегай стандартного коричневого окрашивания Minecraft-сущностей. Цвет должен соответствовать текстуре модели.

Модель должна правильно ориентироваться относительно направления полёта.

Если полноценная модель требует отдельного инструмента, подготовь совместимые ресурсы, экспортируемую геометрию и инструкции по доработке. Не выдавай примитивный куб за завершённую модель.

## 6. FPV-камера и интерфейс

При подключении камера должна показывать мир от лица дрона, а не игрока.

Изображение занимает весь экран.

Поверх изображения рисуется фирменный FPV-HUD.

HUD должен содержать:

- Скорость.
- Высоту.
- Заряд батареи.
- Уровень сигнала.
- Направление.
- Крен и тангаж.
- Время полёта.
- Состояние двигателя.
- Идентификатор подключённого дрона.
- Статус видеосвязи.
- Небольшой логотип компании.

Стиль: технологичный интерфейс FPV-очков с минималистичными элементами, читаемым текстом и аккуратной графикой.

HUD не должен сильно закрывать изображение.

Добавь переключение между минимальным и расширенным HUD.

При подключении показывай короткую анимацию:

BOOTING...
SEARCHING FOR DRONE...
HANDSHAKE COMPLETE
VIDEO LINK ESTABLISHED

Основной язык интерфейса — украинский. Подготовь также английскую и русскую локализации.

## 7. Звуки

Реализуй отдельную звуковую систему для дрона:

- Запуск двигателя.
- Холостой ход.
- Увеличение оборотов.
- Полёт на высокой скорости.
- Пролёт дрона мимо игрока.
- Радиопомехи.
- Подключение и отключение оборудования.
- Предупреждение о низком заряде.
- Потеря связи.
- Столкновение и игровой взрыв.

Частота и громкость двигателя должны зависеть от игровой скорости и тяги.

Другие игроки должны слышать звук с позиции дрона, с естественным затуханием по расстоянию.

Пилот в очках должен слышать отдельный приглушённый аудиоканал.

Если качественные звуковые ассеты невозможно создать автоматически, реализуй систему воспроизведения и укажи точные пути для их добавления. Не используй чужие защищённые звуки без разрешения.

## 8. Столкновения и уничтожение

При сильном столкновении дрон уничтожается.

В игровом мире появляется эффект взрыва.

В конфигурации должны быть доступны:

- Включение и отключение разрушения блоков.
- Настройка силы игрового взрыва.
- Включение и отключение урона сущностям.
- Ограничение количества активных дронов.
- Настройка перезарядки или задержки повторного запуска.

После столкновения у пилота:

1. Изображение резко искажается.
2. Появляются короткие помехи.
3. Камера теряет связь.
4. Экран становится тёмным.
5. Появляется надпись «НЕМАЄ СИГНАЛУ».
6. Игрок может выйти из FPV-режима отдельной клавишей.

Не возвращай игрока автоматически в обычную камеру до завершения эффекта, если он не нажал выход.

## 9. Кинематографический реплей

Разработай систему повторов последних секунд полёта.

Это важная и желательная функция.

На сервере фиксируй историю движения дрона с временными отметками.

Для каждого дрона достаточно хранить ограниченный кольцевой буфер последних 10 секунд.

Воспроизведение должно иметь:

- Камеру от третьего лица.
- Возможность повторить последние секунды.
- Замедленное воспроизведение.
- Кинематографический ракурс.
- Кнопку пропуска.
- Возможность отключения реплеев.

По возможности добавь свободную камеру.

Реплей не должен повторно создавать взрывы, наносить урон или изменять игровой мир.

Если точная запись всего состояния мира слишком сложна, реализуй облегчённый реплей траектории дрона с визуальным воспроизведением событий.

В мультиплеере реплей должен показываться конкретному игроку, не останавливая сервер и не прерывая игру других участников.

Чётко документируй ограничения системы.

## 10. Дополнительные режимы

Добавь архитектуру для следующих игровых режимов.

**Training Mode**

Дрон для тренировок, который можно безопасно посадить и повторно использовать.

**Race Mode**

Гонки через контрольные точки с таймером.

**Spectator Mode**

Один игрок управляет дроном, другой может подключиться к видеокамере только для наблюдения с разрешения владельца.

**Night Vision**

Игровой фильтр ночного видения с характерным зелёным оттенком.

**Black Box**

Информация о последнем полёте: длительность, максимальная скорость, высота и причина завершения.

Приоритет — сначала завершить основную механику, затем расширенные режимы.
